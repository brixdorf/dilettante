In my [last blog](https://blog.romitraj.dev/blog/why-you-should-own-a-server), I laid down the reasons and benefits of owning a server. But, our job doesn't stop at just getting a server, we need to properly set it up. The most important part of a server is how you access it. Considering this is going to be your main online space, you should treat it the same as how you treat your personal belongings. And the first step, is the properly secure it.

In order to access your server, you are required to use something called **SSH** which stands for Secure Shell. It is basically an encrypted tunnel which protects the data passing through it so nobody can eavesdrop it. You will need a SSH client for this. Although SSH is preinstalled in Linux and Mac and [Putty](https://putty.software/) is the default goto in Windows, I will suggest you to use [Termius](https://termius.com/) instead. It provides a clean GUI and a really simple interface to work with.

Now, before we move on, I want to ask you a very important question. Do you use a password manager? If your answer is no, then the first thing you should do, my friend, is create an account in [Bitwarden](https://bitwarden.com/) and use that as your default password manager. Import all your existing passwords to it, download their apps and use it. Store all your credentials related to your server inside it.

I am not joking, if you are not using a password manager in 2026, you are making a truly grave mistake.

Keep in mind, you must remember the master password. This is the only one you need for Bitwarden. Write it down somewhere safe.

Now, how do you connect to your server? You do so by a unique IP address assigned to it. Although IPV6 is the modern standard, it is recommended to use IPV4 addresses right now for better compatibility.

Enter your username and server IP in Termius and login.

Whenever you rent a server from a provider (for e.g. [OVHcloud](https://www.ovhcloud.com/en-in/vps/)), you are initially given a default username and a temporary password. You are required to change the password on your first login, after doing so, note down the new password (in a password manager) and continue from here.

⚠️ Keep in mind this guide is based on **Ubuntu Server 26.04**

1. ### Initial login and creating a new user

The very first command that you should run in your server is, of course

```bash
sudo apt update && sudo apt upgrade -y
```

Updating the system is paramount. If it asks you to reboot, just do `sudo reboot`.

You should now create a new user with root permissions. Run

```bash
sudo adduser <your-username>
```

You will be asked to provide a full name and some personal details, just skip them.

And to give it `sudo` permissions, run

```bash
sudo usermod -aG sudo <your-username>
```

*`-aG` means append group*

To check if your user now has `sudo` permissions, run

```bash
groups <your-username>
```

If it returns `sudo`, you are good to go.

Now why did we create a new user? Well, default usernames in most installs are the distro names (e.g. `ubuntu`) and they are pretty easy to guess. Creating a new `root` user gives you more flexibility and less chance for attackers to guess it.

2. ### Generating a new SSH key

In Termius, go to the keychain section and generate a new key. Use the default key type, use a strong passphrase (generate it using a password manager) and then you will get a public-private key pair. You will use this to login to your server. Save them.

3. ### Setting up key-based login for your new user

In order to switch to your new user, run

```bash
sudo su - <your-username>
```

*`su` means switch user*

Now, we have to create a `.ssh` folder inside our home directory. Give all permissions to the owner for this folder.

```bash
mkdir -p ~/.ssh
chmod 700 ~/.ssh
```

Now, you have to append your newly generated public key in Termius to a `authorized_keys` file inside `.ssh`

```bash
echo "ssh-ed25519 xxx... Generated By Termius" >> ~/.ssh/authorized_keys
```

Lock down the permission for the `authorized_keys` file

```bash
chmod 600 ~/.ssh/authorized_keys
```

SSH is done now. You should be able to login using your private key. Keep the existing terminal window open, connect a new session, use your newly generated username but this time use your private SSH key instead of your password, you may get a prompt to save to known hosts, accept it and hopefully you are in a new SSH session.

Run

```bash
whoami
sudo whoami
```

If you see `<your-username>` and `root`, congrats, you have successfully connected a passwordless SSH session.

4. ### Disabling password based login

After you are successfully able to connect to remote sessions through SSH, it is time to remove the deadweight, them being password based logins. See, when attackers target a server, they try to guess the user's password through various methods (like brute forcing, dictionary attacks etc.), so by disabling the password login entirely, we can essentially kill the entire attack vector from the start.

Also, ensure that you have properly authenticated your SSH keys, because once you turn password based login off, you cannot access your server if you lose your keys (yet another reason to use a password manager like Bitwarden).

You have to create create a file called `01-hardening.conf`

```bash
sudo tee /etc/ssh/sshd_config.d/01-hardening.conf > /dev/null << 'EOF'
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
EOF
```

What the above command does is toggling the `PasswordAuthentication` method as false. `KbdInteractiveAuthentication` is another method of login that should be toggled off as well.

The file created has a `01` prefix because the drop in configs in SSH are considered as per first value, so `01` beats whatever default config your provider has set.&#x20;

After you modify it, run

```bash
sudo sshd -t
```

to verify that the syntax is correct.

Now restart SSH

```bash
sudo systemctl restart ssh
```

After this, run

```bash
sudo sshd -T | grep -iE 'passwordauthentication|kbdinteractive'
```

It it returns `passwordauthentication no` and `kbdinteractive no`, then congrats, password based login is now disabled in your system.

5. ### Enabling firewall (ufw)

**ufw** stands for Uncomplicated Firewall. It is the default firewall installed in most servers. To configure it, first enable support for SSH, so it doesn't block your login connections.

```bash
sudo ufw allow 22/tcp
```

After this, set the default policies

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
```

And then enable it

```bash
sudo ufw enable
```

To check if everything is correct, run

```bash
sudo ufw status verbose
```

If all is ok, the firewall is also configured now.

6. ### Enabling fail2ban

Now what even is **fail2ban**? Well, it is a tool to ban IPs who are repeatedly pinging (and failing) to login to your server, essentially the bad actors.

Install it first,

```bash
sudo apt install fail2ban -y
```

Now you have to create a local `.jail` config file. This specifies the rules for this service, below are some good defaults

```bash
sudo tee /etc/fail2ban/jail.local > /dev/null << 'EOF'
[DEFAULT]
bantime = 30m
findtime = 10m
maxretry = 3

[sshd]
enabled = true
EOF
```

Check the config

```bash
sudo fail2ban-client -t
```

Now restart it

```bash
sudo systemctl restart fail2ban
```

And see its status

```bash
sudo fail2ban-client status sshd
```

If it comes out right, all good. Moving on to..

7. ### Base hardening

These are some additional security steps which strengthen your server even more.

Confirm that the `root` login is disabled

```bash
sudo sshd -T | grep -i permitrootlogin
```

It should return `no`.

Now, we should delete the default user that was created automatically by the vendor. To check which users are currently logged in, run

```bash
loginctl list-sessions
```

Terminate all the `ubuntu` sessions

```bash
sudo loginctl terminate-user ubuntu
```

Delete the temporary user and its home directory

```bash
sudo userdel -r -f ubuntu
```

After this, reboot

```bash
sudo reboot
```

8. ### Changing the default SSH port

The default SSH port is `22`, and hence this is the port most attackers use to brute force a login. If we simply change it to something random, they will have no known port to connect to.

Keep in mind, you should keep running your active SSH session, since if you do something wrong, you can undo it here.

Pick a random number between [20K-30K](https://www.random.org/integers/?num=1\&min=20000\&max=30000\&col=1\&base=10\&format=html\&rnd=new), this will be your port.

We will pick `23117` for this session (do not use the same!).

Allow it in firewall

```bash
sudo ufw allow 23117/tcp
```

Update **fail2ban** setup

```bash
sudo sed -i '/^\[sshd\]/a port = 23117' /etc/fail2ban/jail.local
```

Restart it

```bash
sudo systemctl restart fail2ban
```

Now you need to create a systemd socket override. This is to ensure that the port is reflected system-wide. Run

```bash
sudo systemctl edit ssh.socket
```

This will open an override file. Only change the following, don't touch anything else!

```bash
[Socket]
ListenStream=
ListenStream=0.0.0.0:23117
ListenStream=[::]:23117
```

Reload systemd and restart the SSH socket and service

```bash
sudo systemctl daemon-reload
sudo systemctl restart ssh.socket
sudo systemctl restart ssh.service
```

To see status run

```bash
sudo systemctl status ssh.socket
```

Finally check if both IPV4 and IPV6 connections are listening to the new port

```bash
sudo ss -tlnp | grep 23117
```

Should show `0.0.0.0:23117` and `[::]:23117`

Now, connect a new SSH session with the new port, keep the old one active.

If you are able to connect. Congrats, you just got a brand new SSH port. Now let's deactivate the old ones.

Remove port `22` from ufw

```bash
sudo ufw delete allow 22/tcp
```

Now, from your local machine (not server) run

```bash
# From your local machine (linux command):
nc -zv -w 5 <server-ip> 22
```

You should see that the connection is timed out. This proves old SSH port is being blocked by firewall.

9. ### Renaming your server

Who doesn't like to name their precious possessions? Well, this server is one of yours, so name it. We will choose `augustus` for this session. Run

```bash
sudo hostnamectl set-hostname augustus
```

Verify with

```bash
hostnamectl
```

Edit `/etc/hosts` to match

```bash
sudo nano /etc/hosts
```

Add `127.0.0.1` (augustus) to

```bash
127.0.0.1    localhost
127.0.1.1    augustus
```

Now finally reboot

```bash
sudo reboot
```
